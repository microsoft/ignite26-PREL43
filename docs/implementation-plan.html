Cowork Lab on Skillable

Hydration and scoring for the Copilot Cowork lab, built entirely inside Skillable as PowerShell scripts. Every participant gets a fresh Microsoft 365 tenant; nothing is deployed in Azure.

1. Summary and decisions

Part 1
Hydration

One life cycle action at First Displayable runs the HelixKit scripts from an ISO attached to the lab VM and fills the participant's tenant with the Helix launch story before the event.

Part 2
Scoring

Five scored Activities (12 check scripts) run when the participant clicks Check my work; Skillable records the score.

Language
PowerShell 7

Hydration: "Execute Script in Virtual Machine" (HelixKit on removable media). Scoring: "Execute Script in Cloud Platform". Both use Skillable's per-tenant cloud credential.

Infrastructure
None

No Azure deployment and no file hosting: the data pack travels inside the ISO. Results live in Skillable's reports.

DecisionDetail
Two parts onlyHydration and scoring, both inside Skillable. No external scoring service, leaderboard or scorecard site (Option 1).
One tenant per participantSkillable provisions a fresh M365 tenant per participant (10 E7 fictional users, Cowork credits included) and tears it down when the lab ends.
CredentialsAll scripts use Skillable's per-tenant cloud credential (@lab.CloudCredential(…)), which has the Graph permissions needed. We register no apps in participant tenants.
Dev/test tenant9e9dab93-f5bd-40b1-bed8-59a535fe26c0: a test app registration there mirrors the Skillable credential's permissions so scripts can be run by hand. Whether it matches the pool template is unknown, so every script runs a pre-flight check.
When hydration runsAt First Displayable (VM scripts cannot run at Post-Build) of pre-built lab instances, so Microsoft 365 has hours to index content before participants arrive.
Why an ISOSkillable passes a cloud script to PowerShell as one command-line argument, so large scripts fail ("argument list too long"). Hydration (about 370 KB with the data pack) therefore runs inside the pre-built VM from removable media; the 12 check scripts stay small (16–20 KB) and run in the cloud.
Dates in the storyRelative to the event day ($EventDate at the top of the life cycle script). Skillable pre-builds from D−1 09:30 in the event time zone, because Teams import refuses future-dated posts.
Source of the content and checksThe existing Cowork-Lab data pack (helix-datapack-1.0.0.zip) and scorecard.json (12 checks, 100 points, pass mark 70). Logic is ported from the glc_hydrate engine.

Why "End lab" and no Repeat on hydration: a tenant that failed hydration must never reach a participant. Skillable re-runs an uncaught script error every 60 seconds for up to 30 minutes, so the scripts catch their own errors, fail clearly once, and let Skillable discard the instance.

Pre-instancing

Pre-build the expected number of participants plus a 15% buffer, starting D−1 09:30 in EventTimeZone. Instances that fail the Prepare Helix workspace action end automatically and are not assigned.

4. Part 1: Hydration

4.0 Pre-flight check (step 1 of the action)

Runs first and writes nothing. Signs in with the cloud credential and checks, grouped by what needs them, every Microsoft Graph application permission used by hydration, readiness, scoring and TAP; that the learner exists and is licensed; that at least 6 other licensed users have mailboxes for the Helix organisers; and that EventDate and EventTimeZone are set. If anything is missing, the lab ends with one readable list. The hydrate script repeats the permission check as a safety net.

4.1 Hydrate (step 2)

#PhaseWhat it does
1Credential blockThree lines: tenant ID, client ID and secret from @lab.CloudCredential(…); learner = the launch's Office 365 admin (published as @lab.Variable(LearnerUpn)). The secret reaches the kit through an environment variable, never the command line.
2Time windowComputes D from EventDate and EventTimeZone. Before D−1 09:30 or after D: stops with "outside hydration window" and writes nothing.
3Pre-flightSigns in; reads the permissions in the token and lists any missing (User.ReadWrite.All, Mail.ReadWrite, Calendars.ReadWrite, Files.ReadWrite.All, Teamwork.Migrate.All, Group.ReadWrite.All, TeamMember.ReadWrite.All, MailboxSettings.ReadWrite); confirms the learner exists with E7 and Copilot licences; discovers the licensed fictional users (at least 6 needed).
4Data packLoads the Helix data pack embedded in Hydrate.ps1 on the ISO.
5PersonasMaps the 6 Helix meeting organisers onto discovered licensed users (display name, title, department, manager, photo); creates the rest of the Helix cast as unlicensed accounts, reusing existing ones. Never assumes specific user names.
6Learner profileTime zone and locale; bounded wait until the learner's mailbox and OneDrive exist.
7TeamsMigration-mode team and channel, backdated posts (D−3 … D−1), complete migration, learner as owner, personas as members.
8Channel filesUploads the 8 Helix files (launch plan, spec, pricing, sync notes, competitor PDFs).
9MailBackdated, threaded, received (not draft), unread messages, using the same MAPI properties as the current engine.
10CalendarOrganisers create the Helix meetings, the learner accepts them, and the leftover invitation messages are removed.
11FinishSet-LabVariable HydrationStatus ok and HydratedAt. No other output.

4.2 Readiness (step 3)

  • The six day-one items are present: Helix team and posts, mail threads, channel files, accepted meetings, learner licences, learner mailbox ready.
  • No scoring check passes on the fresh tenant, so nobody can score without doing the work.
  • Sets ReadinessStatus to ok or the reason; ends the lab on failure.

4.3 Learner sign-in

Learners sign in with each launch's Office 365 admin (AdministrativeUsername / AdministrativePassword in Lab Access) and set up Microsoft Authenticator on first sign-in. The Learner step makes sure the admin has a licence that includes Copilot. Cowork being enabled and Copilot credits must come with Skillable's tenant.

4.4 Rules for every hydration script

  • Safe to re-run: each phase checks the tenant before writing ("team already exists?"), so a retry finishes the job without duplicates.
  • Throttling: every Graph call retries on 429/503 and honours Retry-After.
  • Seed rule kept: no seeded mail, post, event, file name or content contains a scoring phrase (enforced by the data pack build).
  • Quiet: no data written to output, per Skillable guidance; results go into lab variables.
  • Data pack: the 240 KB pack is embedded in Hydrate.ps1 on the ISO; nothing is hosted or downloaded.
  • Expected time: 10–15 minutes per tenant; measured in the pilot.

5.5 End-of-lab score

When the lab is submitted or ends, Skillable's platform scoring totals the five Activities. That total is the participant's official result in Skillable's reports. verify that platform scoring evaluates Activities the participant never clicked; if not, the lab guide's last page asks them to click Check my work on every milestone before submitting.

7. What organisers see

  • Skillable reports: each participant's activity results and total score, with export, from Skillable Studio.
  • Live progress during the event: Skillable's lab instance monitoring (which Activities each participant has passed).
  • Disputes: an organiser opens the participant's lab instance in Skillable and re-runs the Activity, or adjusts the score in Skillable.
Option 1 has no separate leaderboard or scorecard website. If a live cross-participant leaderboard is wanted later, the check scripts can additionally send results to a small results service; the scripts change only by a few reporting lines.

Open questions (answer from Skillable, or measure in the dev lab profile):

  • Does First Displayable run while a pre-instance is built? VM scripts cannot use Post-Build. If First Displayable only fires when the learner opens the lab, each learner waits 10–20 minutes for hydration.
  • Maximum life cycle action timeout (hydration needs 10–15 min, planned 45)
  • Can a VM life cycle script call Set-LabVariable? (the status line stays blank otherwise; the action's result is unaffected)
  • Is Set-ActivityResult -Message supported, or should hints come from feedback text / script output?
  • Attempt limits on Activities with retries enabled
  • Does platform scoring at submit evaluate Activities the participant never clicked?
  • Name of the cloud credential in the production lab profile (readable in its Cloud tab)
  • Does the 9e9d tenant match the participant tenant template? (unknown; pre-flight catches gaps)
